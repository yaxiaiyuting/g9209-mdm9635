## 0. 摘要（TL;DR）

### 0.1 一句话结论
**AP（应用处理器）侧已完全打通**：我们自写的静态 ARM64 Sahara 加载器能完整地、逐块地被 modem 接受地
喂完全部 12 个固件镜像（每个都收到 modem 自己的 `status=0` 确认）。**当前唯一卡点**是：
modem 收完固件后**不执行**（不进入 AMSS，不拉高 `MDM2AP_STATUS`）。
因此**目前仍不能读卡/上网**——SIM 卡座物理上挂在这颗外挂 modem 上。

### 0.2 已完成（均有实测证据）

| # | 成果 | 关键证据 |
|---|---|---|
| 1 | Sahara over HSIC 协议**完全逆向** | 帧格式、全部命令、原厂 ks 的字节级行为 |
| 2 | **自写静态 ARM64 Sahara 加载器**（v39） | 12 个镜像全部 `END_IMAGE_TX status=0` |
| 3 | **完整 ramdump**（14 个内存区） | `cpdump/OCIMEM.BIN` 等，含 `ResetStatusRegion`/`MDM_ERR_FATAL` |
| 4 | 内核改动：让 LOS 20 在这台机器上**能正常启动** | 6 处 panic 抑制 + PCIe + SSR 复位路径 |
| 5 | 传输性能：**28 倍提升**（~250 KB/s → **~7 MB/s**） | `61,645,808 B / 8.8 s` |
| 6 | 内核 ks_bridge 驱动**聚合转发**（boot-X→AD 六轮） | NAK 从 5/8 → **0**，厂商 ks 首次推进到第 2 个镜像 |
| 7 | 原厂资产全部提取 | `boot.img`、5 个 CHN DTB、CP 包 9 镜像、`ks.real` |

### 0.3 当前卡点（唯一）
modem 接收完 12 个镜像后**停留在自己的 PBL**，不跳转到已加载的固件：
- `MDM2AP_STATUS` 始终为低（modem 未宣告"运行中"）
- USB 一直是 `05c6:9008`（PBL 阶段 PID），从未出现 AMSS 阶段 PID
- 从未出现 `/dev/efs_hsic_bridge`

### 0.4 已彻底排除的怀疑（重要，省后来者时间）

| 怀疑项 | 结论 | 证据 |
|---|---|---|
| 镜像内容错误 | ✗ 排除 | 设备上 9 个镜像与原厂 CP 包**逐字节一致**（md5 9/9） |
| EFS 内容错误 | ✗ 排除 | 设备 `m9kefs1` 是**真 EFS**（`IMGEFS1$` + 真实数据）；原厂 CP 包里反而是 `IMGEFS- DUMMY-1` |
| DTB 配置错误 | ✗ 排除 | CHN 与 EUR 的 `qcom,mdm1`（`ext-mdm9x35`）节点**结构完全一致**（9 个 GPIO、ramdump 参数、sysmon-id 全同） |
| 传输协议用错 | ✗ 排除 | 自写加载器按请求长度整块发送 → 12 镜像全 `status=0` |
| 内核不稳定 | ✗ 排除 | 连续多轮 `panic=0`（修复后） |
| AP 侧干扰 | ✗ 排除 | 已逐一消除（见 §6） |

## 1. 设备与背景

### 1.1 硬件架构
```
┌──────────────────────────────┐        ┌───────────────────────────┐
│ Exynos7420 (AP)              │        │ Qualcomm MDM9635          │
│  - 4×A57 + 4×A53             │  HSIC  │  - PBL / SBL1 / TZ / RPM  │
│  - RAM / eMMC (UFS)          │◄──────►│  - AMSS (qdsp6sw 56MB)    │
│  - 无集成基带 ✗               │  USB2.0│  - 自己的 DDR / EFS 分区  │
│                              │ 480Mbps│  - ★ SIM 卡座挂在这里     │
└──────────────────────────────┘        └───────────────────────────┘
        │                                         ▲
        └── GPIO: AP2MDM_STATUS / SOFT_RESET / HSIC_READY / VDDMIN / ERRFATAL
            MDM2AP: STATUS / PBLRDY / ERRFATAL / VDDMIN
```
关键点：**这台机器的 SIM 卡座不接 AP，而接在外挂 MDM9635 上**。所以"读卡/上网"= modem 必须先跑起来。

### 1.2 原厂软件栈
| 组件 | 路径 | 作用 |
|---|---|---|
| `cbd` | `/vendor/bin/cbd` | Coprocessor Boot Daemon：触发 modem 上电/引导 |
| `mdm_helper` | `/vendor/bin/mdm_helper` | 注册 ESOC req engine、上电、调 ks 喂固件、等待 modem 启动 |
| `ks` (kickstart) | `/vendor/bin/ks` | 通过 `/dev/ks_hsic_bridge` 跑 Sahara 协议喂镜像；含 dump / 命令模式 / EFS 同步 |
| 内核驱动 | `ext-mdm` / `esoc` / `ks_bridge` / `efs_hsic_bridge` | GPIO 电源时序、HSIC 链路、字符设备桥 |

原厂 `mdm_helper` 调 ks 的完整命令行（实测抓到）：
```
ks -w /cpdump/ -p /dev/ks_hsic_bridge -r 21 \
   -s 21:/firmware/image/sbl1.mbn  -s 25:/firmware/image/tz.mbn \
   -s 30:/firmware/image/sdi.mbn   -s 23:/firmware/image/rpm.mbn \
   -s 31:/firmware/image/mba.mbn   -s 8:/firmware/image/qdsp6sw.mbn \
   -s 28:/firmware/image/dsp2.mbn  -s 6:/firmware/image/apps.mbn \
   -s 16:/dev/block/modem/m9kefs1  -s 17:/dev/block/modem/m9kefs2 \
   -s 20:/dev/block/modem/m9kefs3  -s 29:/firmware/image/acdb.mbn
```

### 1.3 为什么 LOS 20 读不到卡
LOS 20 的 vendor 来自**国际版 S6（G920F / `zerofltexx`，Shannon 集成基带）**，
而非 G9209 的高通方案。实测：
```
ro.build.description = zerofltexx-user 7.0 NRD90M G920FXXU6EVG1     ← 国际版
gsm.sim.state / gsm.operator.alpha / gsm.network.type               ← 全为空
无 rild / qmuxd 进程；/dev 下只有 diag，无 smd/qmi/efs
```
→ 结论：想让 LOS 20 读卡，**必须**把 modem 跑起来 **并** 移植高通 QMI/RIL 用户态。

| # | Sahara ID | 文件 | 大小 | 作用 |
|---|---|---|---|---|
| 1 | 21 | `sbl1.mbn` | 182,584 B | **Secondary Boot Loader**：PBL 之后第一级，初始化 DDR，校验并拉起 TZ/RPM/SDI/MBA |
| 2 | 25 | `tz.mbn` | 336,248 B | **TrustZone / QSEE** 安全世界固件 |

| 6 | 8 | `qdsp6sw.mbn` | **56,079,232 B** | ★ **AMSS 主体**：协议栈/射频/基带逻辑（占总量 83%） |
| 7 | 28 | `dsp2.mbn` | 5,147,988 B | 第二 DSP 子系统（音频/传感器等） |
| 8 | 6 | `apps.mbn` | 3,359,376 B | modem 内部应用核镜像 |

总搬运量 ≈ **67 MB**。

### 2.2 会话模型（重要发现）
**`每个镜像一个新 Sahara 会话`是正常的**：启动链上每一级引导（PBL→SBL1→…）都会自己重跑一次 Sahara。
实测：一次完整加载 = **12~13 个 HELLO 会话**，每镜像一个。
（反证：若对 `END_IMAGE_TX` 不作应答，则只出现 1 个 HELLO 并停住。）

## 3. Sahara over HSIC 协议逆向（核心章节）

### 3.1 帧格式
**实测**（由 `ks_bridge` 驱动的收发日志与 hexdump 得出）：
```
+--------+--------+-------------------+
| cmd u32| len u32| payload (len-8)   |     全部小端；共 len 字节
+--------+--------+-------------------+
无 HDLC、无 CRC、无转义。
```
| cmd | 名称 | 方向 | 说明 |
|---|---|---|---|
| 0x01 | HELLO | dev→host | 携带 version/min/max_cmd_len/mode |
| 0x02 | HELLO_RESP | host→dev | **原厂 ks 实测为固定 48 字节**（见 3.2） |
| 0x03 | READ_DATA | dev→host | 请求 `(image_id, offset, length)` |
| 0x04 | END_IMAGE_TX | dev→host | 本变体中由 **modem** 发出，表示"某镜像收完"，带 `status` |
| 0x05 | DONE_REQ | host→dev | 对 END_IMAGE_TX 的正确应答 |
| 0x06 | DONE_RESP | dev→host | modem 确认 |
| 0x07 | RESET_REQ | host→dev | ★ **重启 modem**（会擦掉刚加载的固件，不可当"开始执行"用） |
| 0x09 | MEMORY_DEBUG | dev→host | 交出内存区表（ramdump 用） |
| 0x0A | MEMORY_READ | host→dev | 请求读内存区 |
| 0x0B | MEMORY_READ_DATA | dev→host | 原始内存数据（**无帧头**） |
| 0x0E | CMD_READY | dev→host | ★ 命令模式入口 |
| 0x0F | CMD_SWITCH_MODE | host→dev | 长度 12（实测原厂 ks 行为） |
| 0x10/0x11/0x12 | CMD_EXEC / RESP / DATA | 双向 | 命令执行与数据 |

### 3.2 HELLO 与 HELLO_RESP（字节级）
modem 的 HELLO（48 字节）：
```
01 00 00 00 | 30 00 00 00 | 02 00 00 00 | 01 00 00 00 | 00 04 00 00 | 00 00 00 00 ...
cmd=1        len=48        version=2     version_min=1  max_cmd_len=0x400  mode=0
```
**原厂 ks 的 HELLO_RESP 不是回显**，而是固定内容（我们抓到的实际字节）：
```
02 00 00 00 | 30 00 00 00 | 02 00 00 00 | 02 00 00 00 | 00 00 00 00 ...
cmd=2        len=48        version=2     version_min=2  max_cmd_len=0
```
（`mode` 字段按 modem 的 HELLO 回显：镜像模式回 0，命令模式回 2。）

### 3.3 数据服务的正确姿势（决定成败）
1. 收到 `READ_DATA(id, offset, len)` → **必须把该请求的 `len` 字节完整发出**；
2. 分块可以大于一次写，但**总量必须精确等于请求长度**；
3. 请求长度可能很大（实测 tz 有 **174,920 B** 的单次请求）；
4. 发完该请求的全部数据后，modem 会继续下一个 `READ_DATA`（可能换镜像）；
5. 每个镜像收完后 modem 发 `END_IMAGE_TX(id, status=0)` → 主机回 **`DONE_REQ`** → modem 回 `DONE_RESP`；
6. **不要**在每个镜像后发 `RESET_REQ`（那会让它重启并重新索要镜像 ✗）。

### 3.4 MEMORY_DEBUG 与 ramdump
modem 会发 `cmd=9 (MEMORY_DEBUG)`，载荷是**内存中的区域表**（我们用 `MEMORY_READ` 把它读回来）：
表项为**定长 52 字节**：
```
struct { u32 type; u32 addr; u32 len; char name[20]; char file[20]; }
```
实测 14 个区（部分）：
| 名称 | 地址 | 长度 | 文件 |
|---|---|---|---|
| OCIMEM | 0xfe800000 | 34,816 | OCIMEM.BIN |
| RPM Code RAM region | 0xfc100000 | 131,072 | CODERAM.BIN |
| RPM Data RAM region | 0xfc190000 | 65,536 | DATARAM.BIN |
| RPM MSG RAM region | 0xfc428000 | 16,384 | MSGRAM.BIN |
| LPASS LPM region | 0xfe100000 | 16,384 | LPM.BIN |
| IPA 1/2/3 region | 0xfd4c0000 … | 102,396 / 36,860 / 8,444 | IPA_REG*.BIN |
| IPA uC iram/dram | 0xfd4f0000/0xfd4f4000 | 4,096 / 7,936 | IPA_IRAM/DRAM.BIN |
| ResetStatusRegion | 0x07fb64d8 | 4 | ResetStatusRegion.BIN |
| PmicPONstat | 0x07fb64e0 | 8 | PmicPONstat.BIN |
| MDM_ERR_FATAL | 0x011146d8 | 4,224 | MDM_ERR_FATAL.BIN |
| CMMScript | 0x07fa9320 | 1,212 | CMMScript.BIN |
另外 modem 随表提供一个 **CMM 脚本**（文本），其首行即固件版本：
```
; Build ID: 9x35A-AAAHANAZA-40000000
```
我们实测读回的 `ResetStatusRegion = 02 00 00 00`、`PmicPONstat = 20 00 02 00 02 00 00 00`。

### 3.5 命令模式（原厂 ks 的路径，反汇编确认）
从设备上的 `/system/bin/ks.real`（ARM64、39,272 B、stripped）反汇编得到：
```
STATE <-- SAHARA_WAIT_COMMAND
  RECEIVED <-- SAHARA_END_IMAGE_TX  → SENDING --> SAHARA_DONE      (0x05)
  RECEIVED <-- SAHARA_READ_DATA     → 供数据
  RECEIVED <-- SAHARA_MEMORY_DEBUG  → SENDING --> SAHARA_MEMORY_READ
  RECEIVED <-- SAHARA_CMD_READY (0x0E)      ← 命令模式入口（0x49ac: cmp w4,#0xe）
       → 取包内 mode 字段（偏移 12）；发 CMD_SWITCH_MODE(0x0F, 长度 12)（0x49d8/0x49e8/0x4a0c）
```
ks 内含 `efssyncloop` / `memdump` / `ramdumpimage` / `commandop.bin` 等实现——
**这正是"EFS 同步 / 命令阶段"那段我们自写加载器尚未实现的逻辑**。

### 3.6 一个容易误判的现象
在**每镜像一个会话**的模型下，`END_IMAGE_TX(id, status)` 里的 `status` 字段实测会出现 `0 / 1 / 5 / 0x400`。
其中 `0x400` 不是错误码，而是**块大小 1024**（早期版本的 modem 用它表达"每块 1024"）。
只有在 `status==0` 时才是"该镜像成功"。

## 4. 工具链

### 4.1 自写静态 ARM64 Sahara 加载器 —— `tools/sahara.c`
*无 libc、无动态链接、纯 syscall*，静态 ARM64，可直接 push 到 `/data/local/tmp/` 运行。
当前版本 **v39**，能力：

| 能力 | 说明 |
|---|---|
| 握手 | 解析 HELLO，回 **与 ks 逐字节一致** 的 HELLO_RESP（含 mode 回显） |
| 镜像服务 | 按 `READ_DATA` 请求**整块**发送（单次可 >64KB），文件 fd **缓存**（性能关键） |
| 结束流程 | 对 `END_IMAGE_TX` 回 `DONE_REQ`；**不发** `RESET_REQ` |
| ramdump | 解析内存区表（52B 表项）→ 逐区 `MEMORY_READ` → 落盘 `/data/local/tmp/diag/cpdump/*.BIN` |

| 诊断 | 非阻塞 `ppoll` 超时、逐字节重同步、吞吐统计、写阻塞检测、`ESOC_SET_CRASH` |
| 自愈 | 启动前校验自身大小，可从 `ldrx.bak` 自动恢复（设备端文件曾被莫名截断） |

性能实测（缓存 fd 前后）：
```
优化前 ~250 KB/s（整轮 250–300 s）→ 优化后 61,645,808 B / 8.8 s ≈ 7 MB/s   （提升 28×，原厂基线 ≥1.1 MB/s）
```

## 5. 内核改动（逐项）

基线：LineageOS 20 内核（`universal7420`，3.10.108），分支 `mdm-feasibility`。

| # | 文件 | 改动 | 原因/证据 |
|---|---|---|---|
| 1 | `drivers/pci/host/pci-exynos.c` | PCIe 链路失败 `panic()` → 打印错误并返回 | 否则开机即 `PCIE LINK UP FAIL` 卡第一屏 |
| 2 | `drivers/esoc/esoc-mdm-drv.c` | boot_done 等待 `60000 ms` → **`900000 ms`** | flashless boot 需要逐镜像会话，60s 必超时 → SSR 直接 shutdown 把 modem 掐死 |
| 3 | `drivers/esoc/esoc-mdm-drv.c` | boot 超时的 `panic()` → `-EIO` | 与 #2 同源 |
| 4 | `drivers/esoc/esoc_dev.c` | `ESOC_PANIC` → `-EINVAL` | 防止用户态误触发 panic |
| 5 | `arch/arm64/mach-exynos/subsystem_restart.c` | 5 处 `panic()` → `pr_err`；并**恢复** `RESET_SOC` 分支里的 `__subsystem_restart_dev(dev)` | 前者防卡屏；后者让用户态能复位 modem（`echo restart > .../msm_subsys/esoc0`） |
| 6 | `drivers/usb/misc/ks_bridge.c` | **写路径聚合转发**（见下） | 原厂 ks 以 4 字节为粒度写，直接转发会被 modem 判 `NAK 5/8` |

### 5.1 ks_bridge 聚合转发（六轮迭代，每轮都先验证手机能正常启动）
| 版本 | 改动 | 实测 |
|---|---|---|
| `boot-X` | 仅聚合 ≤8B 碎片，按 Sahara 头成帧 | 48B HELLO_RESP 被接受 ✓，NAK 5 消失 |
| `boot-Z` | 三条件（成帧 / 阈值 / 2ms 超时 `delayed_work`） | 暴露缓冲仅 64B ✗ |
| `boot-AA` | **动态 16KB 缓冲**（probe 时 kzalloc） | TX 出现 3204B 真实块 |
| `boot-AB` | **按 modem `READ_DATA` 请求长度分块**（RX 解析 cmd=3） | 3772B ✗（被 2ms 超时抢先） |
| `boot-AC` | **数据路径不设超时** | 31× **4096B 精确块** ✓，ks 首次推进到第 2 个镜像 |
| `boot-AD` | **`req_left` 剩余计数**（支持 174,920B 这类大请求） | ★ **NAK = 0** ✓ |

聚合规则（最终）：
```
ks 写入 <= 8B  →  攒进缓冲，按下列条件之一冲刷：
   (a) 缓冲头部是合法 Sahara 头（len ∈ [8,64]）→ 按该长度成帧（控制包）
   (b) 处于数据请求中（req_left > 0）→ 攒满 min(req_left, 缓冲大小) 即发，并递减 req_left
   (c) 非请求期的兜底 → 2ms 超时冲刷（delayed_work）
>= 9B 的写入 → 原样转发（自写加载器就是这种写法，无需聚合）
```

### 5.2 重要教训：不要在驱动里"想当然"
早期一版（`boot-U`）在**写路径**做帧组装时**空指针 panic**，导致黑屏（`/proc/last_kmsg` 里
`kworker/u16:3 ... ksb_tomdm_work+0x378 ... Kernel BUG at 0`）。
**结论**：驱动改动必须（1）只碰最小面；（2）先只验证"手机能否正常启动"；（3）保留可回滚镜像。

## 6. 环境与实验规程（血泪教训，务必遵守）

### 6.1 六个必须
1. **每轮实验前重启手机**：modem 只有经过一次新的 ESOC 上电（`mdm_subsys_powerup` 且 `mode==PWR_OFF`）
   才会重新枚举 USB；`powerup` ioctl 在 modem 已上电时是**空操作**。
2. **先 `setprop ctl.stop ril-daemon`**（必要时也停 `cpboot-daemon`）：
   否则没有 modem → rild 每 ~5 秒崩溃 → init 触发 `onrestart restart cpboot-daemon`
   → **SIGKILL 整个进程组** ✗，把我们的 `mdm_helper`/`ks`/worker 一起杀掉。
   （实测日志：`init: Sending signal 9 to service 'cpboot-daemon' ... process group`）
3. **`/system/vendor/bin/cbd` 必须是"常驻"版本**：spawn worker 后 `while true; do sleep 60; done`。
   若脚本立刻退出，init 会当作失败服务反复重启 → 同样引发进程组 kill 风暴。
4. **不要用 `pkill -f` / `pgrep -f`**：会匹配到外层 `adb shell` 自身的命令行，
   把自己的 shell 杀掉（表现为 exit 137/143）。一律用 **`pkill -9 -x <comm>`**。
5. **每次 push 后必须校验**（大小 + md5 + 可执行位）：设备端文件曾出现被截断成 0 字节
   （加载器因此"起不来"却毫无报错）。
6. **`/system` 会自己变回只读**：换 `/system/bin/ks` 前必须 `mount -o remount,rw /`，
   否则 mdm_helper 仍调用旧转发器，会与自写加载器**抢端口**。
   ★ 但**绝不要**在 boot 阶段的模块脚本里做 remount/写 `/system`——曾因此导致 **bootloop** ✗。

## 8. 复现指南（从零到"12 镜像全过 + 完整 ramdump"）

### 8.1 准备
```bash
adb push tools/sahara        /data/local/tmp/mdm/ldrx
adb push tools/sahara        /data/local/tmp/mdm/ldrx.bak
adb push tools/mdm_helper    /data/local/tmp/mdm/
adb push tools/powerup tools/esoc_hsic /data/local/tmp/mdm/
adb shell 'chmod 755 /data/local/tmp/mdm/*'
```

### 8.2 每轮实验（务必按序）
```bash
# 1) 停掉 rild 崩溃循环（关键！）
adb shell 'setprop ctl.stop ril-daemon; setprop ctl.stop cpboot-daemon'
# 2) 前提：挂 firmware、建 efs 链接、ks 置空（避免抢端口）
adb shell 'mkdir -p /firmware; mount -t vfat -o ro,shortname=lower /dev/block/platform/15570000.ufs/by-name/RADIO /firmware
           mkdir -p /dev/block/modem
           for p in m9kefs1 m9kefs2 m9kefs3; do ln -sf /dev/block/platform/15570000.ufs/by-name/$p /dev/block/modem/$p; done
           mount -o remount,rw /; printf "#!/system/bin/sh\nexit 0\n" > /system/bin/ks; chmod 755 /system/bin/ks'
# 3) 重启，拿一个"全新的 modem"
adb reboot; # 等待 sys.boot_completed=1
# 4) 加载器 + （仅用于注册 req engine 的）helper
adb shell 'nohup setsid /data/local/tmp/mdm/ldrx >/dev/null 2>&1 </dev/null &'
adb shell 'nohup setsid /data/local/tmp/mdm/mdm_helper >/dev/null 2>&1 </dev/null &'
# 5) 上电 + HSIC
adb shell 'nohup setsid /data/local/tmp/mdm/powerup /dev/subsys_esoc0 >/dev/null 2>&1 </dev/null &'
sleep 8; adb shell '/data/local/tmp/mdm/esoc_hsic'
# 6) 观察
adb shell 'tail -f /data/local/tmp/diag/sahara_own.log'   # 应看到 12 个 END_IMAGE_TX status=0
adb shell 'ls -l /data/local/tmp/diag/cpdump/'            # ramdump 14 个区
```
> 注：加载器 v33+ 会**自己注册 req engine**，因此第 4 步的 helper 可省略（保留亦可）。

| 目标 | 判据 |

| ramdump 成功 | `cpdump/` 下 14 个 `*.BIN`（合计 ~444 KB） |

## 10. 结论

* **协议层与主机侧已彻底解决**：我们不仅能完整喂完 12 个镜像，还能拿到 modem 的内存快照，
  并且把原厂工具链的三大障碍（驱动碎片、init kill 循环、数据分块）逐一消除——

  下一步聚焦"命令模式（`CMD_READY`→`CMD_SWITCH_MODE`→`CMD_EXEC`）"与"原厂成功流程对照"。
* **对使用者的建议**：若目标是尽快恢复"读卡+上网"，原厂 4 件套是最确定的路径（约 1 小时）；
  若坚持 LOS 20，则需要在 A 阶段突破后继续完成 QMI/RIL 移植（数天量级）。
