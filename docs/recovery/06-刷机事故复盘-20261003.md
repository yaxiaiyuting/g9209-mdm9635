# 刷机事故复盘（2026-10-03）：刷原厂 SYSTEM 时掉线 + 数据被迁移

## 一、发生了什么

按计划刷原厂 Android 7.0 做基准对照：
1. `adb push stock-system.img`（3 GB）→ 校验一致 ✅
2. `adb shell dd if=stock-system.img of=.../SYSTEM bs=1M` → **执行 18.9 秒后 adb 掉线** ❌
3. 手机从 USB 总线完全消失；之后靠物理按键进 TWRP 才恢复

进 TWRP 后核对分区状态：
```
BOOT     = 83ba587ca648a3ef   ← 仍是 LOS 20 内核（未被刷，掉线发生在刷它的前一步）
SYSTEM   = 0b82519da0e31104   ← 既不是 LOS20(a1daf6c3) 也不是原厂(f10cd25e) → 写入被打断
RECOVERY = ef70f8e86d245236   ← TWRP 完好（关键退路，全程未动）
```

## 二、恢复过程（已成功）

1. `adb push backup-20261003-full/SYSTEM.img` → 设备端 md5 校验一致
2. TWRP 内 `dd ... bs=1048576` → **27 秒写完 3,187,671,040 字节**（117 MB/s）
3. 回读校验：`BOOT`/`SYSTEM`/`RECOVERY` 三个分区 md5 **与备份逐一相同** ✅
4. `adb reboot` → **LOS 20 正常启动**（`sys.boot_completed=1`，内核 `#28`）

## 三、代价与影响

| 项 | 状态 |
|---|---|
| 系统分区 | ✅ 已由备份完整还原 |
| **/data 用户数据** | ⚠️ **从 5.8 GB 降到 2.8 GB** —— 刷入原厂 system 后，Android 视其为"新系统"做了数据迁移/清理 |
| 备份 | ✅ **USERDATA 的 28 GB raw 完整备份在**，可还原 |
| EFS / m9kefs | ⚠️ `EFS` md5 与备份不同（`1298cf65…` vs `c3494311…`）—— 这是 rild/radio 开机时正常写入；`m9kefs1/2/3` 与备份**完全一致** ✅ |

## 四、★ 教训（下次必须遵守）

1. **绝不在系统运行时 `dd` 刷 SYSTEM**：ext4 已挂载，边刷边被写，既慢又易出问题。
   → **所有 SYSTEM/大分区刷写一律在 TWRP 里做**（TWRP 不挂载 SYSTEM）。
2. **`dd` 的块大小用纯数字**：TWRP 的 toybox `dd` 不认 `bs=4M`，会报
   `block size '4M': illegal number`。用 `bs=1048576`（数字）。
3. **大分区刷写要有"掉线预期"**：刷 3 GB 过程中 adb 可能掉。
   流程要设计成"掉线也能接着做"——
   先 push + 设备端校验，**再**刷；掉线后重新进 TWRP 只重刷未完成那一步即可。
4. **刷完必须"回读校验"**：但注意——
   **SYSTEM/EFS 在系统运行时读到的 md5 必然与备份不同**（已挂载可读写 / 被 radio 写）。
   → **权威校验只在 TWRP 里做**。系统内校验只能用于"确认能启动"。
5. **每次实验前保留 TWRP**：这次能救回来就是因为**从未动 RECOVERY 分区**。
   刷机顺序应把 RECOVERY 放**最后**，或干脆不动。
6. **刷原厂前先单独备份 /data 的文件级快照**（tar），因为刷 system 会触发数据迁移，
   而 raw 备份虽完整但恢复时要整分区回写（28 GB）。
