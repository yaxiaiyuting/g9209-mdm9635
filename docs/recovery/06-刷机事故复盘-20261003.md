# 刷机事故复盘（2026-10-03）：刷原厂 SYSTEM 时掉线 + 数据被迁移

## 一、发生了什么

按计划刷原厂 Android 7.0 做基准对照：
1. `adb push stock-system.img`（3 GB）→ 校验一致 ✅
2. `adb shell dd if=stock-system.img of=.../SYSTEM bs=1M` → **执行 18.9 秒后 adb 掉线** ❌
3. 手机从 USB 总线完全消失；之后靠物理按键进 TWRP 才恢复

进 TWRP 后核对分区状态：
```
BOOT     = 83ba587ca648a3ef   ← 仍是 LOS 20 内核（未被刷，掉线发生在刷它的前一步）
SYSTEM   = 0b82519da0e31104   ← 既不是 LOS20(a1daf6c3) 也不是原厂(f10cd25e) → 写入被打断
RECOVERY = ef70f8e86d245236   ← TWRP 完好（关键退路，全程未动）
```

## 二、恢复过程（已成功）

1. `adb push backup-20261003-full/SYSTEM.img` → 设备端 md5 校验一致
2. TWRP 内 `dd ... bs=1048576` → **27 秒写完 3,187,671,040 字节**（117 MB/s）
3. 回读校验：`BOOT`/`SYSTEM`/`RECOVERY` 三个分区 md5 **与备份逐一相同** ✅
4. `adb reboot` → **LOS 20 正常启动**（`sys.boot_completed=1`，内核 `#28`）

## 三、代价与影响

| 项 | 状态 |
|---|---|
| 系统分区 | ✅ 已由备份完整还原 |
| **/data 用户数据** | ⚠️ **从 5.8 GB 降到 2.8 GB** —— 刷入原厂 system 后，Android 视其为"新系统"做了数据迁移/清理 |
| 备份 | ✅ **USERDATA 的 28 GB raw 完整备份在**，可还原 |
| EFS / m9kefs | ⚠️ `EFS` md5 与备份不同（`1298cf65…` vs `c3494311…`）—— 这是 rild/radio 开机时正常写入；`m9kefs1/2/3` 与备份**完全一致** ✅ |

## 四、★ 教训（下次必须遵守）

1. **绝不在系统运行时 `dd` 刷 SYSTEM**：ext4 已挂载，边刷边被写，既慢又易出问题。
   → **所有 SYSTEM/大分区刷写一律在 TWRP 里做**（TWRP 不挂载 SYSTEM）。
2. **`dd` 的块大小用纯数字**：TWRP 的 toybox `dd` 不认 `bs=4M`，会报
   `block size '4M': illegal number`。用 `bs=1048576`（数字）。
3. **大分区刷写要有"掉线预期"**：刷 3 GB 过程中 adb 可能掉。
   流程要设计成"掉线也能接着做"——
   先 push + 设备端校验，**再**刷；掉线后重新进 TWRP 只重刷未完成那一步即可。
4. **刷完必须"回读校验"**：但注意——
   **SYSTEM/EFS 在系统运行时读到的 md5 必然与备份不同**（已挂载可读写 / 被 radio 写）。
   → **权威校验只在 TWRP 里做**。系统内校验只能用于"确认能启动"。
5. **每次实验前保留 TWRP**：这次能救回来就是因为**从未动 RECOVERY 分区**。
   刷机顺序应把 RECOVERY 放**最后**，或干脆不动。
6. **刷原厂前先单独备份 /data 的文件级快照**（tar），因为刷 system 会触发数据迁移，
   而 raw 备份虽完整但恢复时要整分区回写（28 GB）。

# 六、★ adb 大写入掉线规律（第二轮，2026-10-03 13:30）

## 6.1 实测数据（同一天、同一设备、同一 TWRP）

| 操作 | 环境 | 大小 | 结果 |
|---|---|---|---|
| 刷 SYSTEM | **系统运行时** | 3 GB | ❌ 18.9 s 后掉线 |
| 刷 SYSTEM | **TWRP 内** | 3 GB | ✅ **成功**（27 s @ 117 MB/s）|
| 刷 BOOT | TWRP 内 | 26 MB | ✅ 成功（0.4 s）|
| 刷 RECOVERY | TWRP 内 | 34 MB | ✅ 成功 |
| 刷 **USERDATA** | TWRP 内 | **10 GB** | ❌ **几十秒后掉线，设备离总线** |
| push USERDATA | adb push | 10 GB | ✅ 成功（46 s @ 221 MB/s）|

## 6.2 结论

1. **瓶颈在"单次连续大写入到块设备"**，不在 adb 传输本身
   —— 同样 10 GB 用 `adb push` 写文件系统就成功了（221 MB/s），
   而 `dd` 写块设备则掉线。
2. **约 3 GB 是单次 dd 的安全上限**（3 GB 成功、10 GB 失败）。
3. **"系统运行时刷 SYSTEM"必错**：ext4 已挂载，边写边被改
   —— 既慢（18.9 s 掉线）又危险。**一律在 TWRP 内刷**。
4. **掉线后设备可能从 USB 总线消失**，需物理重启（长按电源 10–20 s）才能回 TWRP。

## 6.3 对策（已实现）

### 设备端：`scripts/flash_resumable.sh`
- 把镜像按块（默认 **256 MB**）写入目标分区（`dd skip/seek`）
- **每块写完立即回读并与源 `cmp` 比对**
- 进度落盘 `/data/local/tmp/.flash_prog_<PART>`
- **掉线重进后自动从第 N 块继续**，不重头来
- 只用 toybox 的 `dd`/`cmp`（TWRP 自带），`bs` 用纯数字（`bs=1048576`）

### 主机端：`scripts/flash-resilient.sh`
- 推送 + 校验设备端镜像（`md5` 一致才继续）
- 调设备端脚本刷写；**掉线就等设备回来再重跑同一条命令**
- 最多重试 30 次，直到输出"全部块完成"
- 支持 `--chunk N` 调整块大小、`--push-only` 只推不刷

### 为什么 256 MB 能行
按 117 MB/s 算，256 MB ≈ 2.2 s/块，远低于掉线出现的几十秒量级
—— 把"一次长写入"拆成"多次短写入 + 每块校验"，绕开了掉线窗口。

## 6.4 后续刷机顺序（建议）

1. `flash-resilient.sh <stock-boot.img> BOOT`（小，快）
2. `flash-resilient.sh <stock-system.img> SYSTEM`（3 GB，**单块也稳**，或用默认 256 MB 分块）
3. `flash-resilient.sh <stock-userdata.img> USERDATA`（10 GB，**必须分块**）
4. 每次都等脚本报"全部块完成"再进下一步
5. 全刷完 `adb reboot`（TWRP 保留在 RECOVERY，作退路）

> 回滚同理：`flash-resilient.sh backup-20261003-full/SYSTEM.img SYSTEM`
