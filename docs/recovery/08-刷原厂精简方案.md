# 刷原厂做基准：精简方案（避开 10 GB 写入）

## 为什么改方案

实测（见 `06-刷机事故复盘-20261003.md` §6）：
- TWRP 内 dd 刷 **3 GB SYSTEM** → ✅ 成功（27 s @ 117 MB/s）
- TWRP 内 dd 刷 **10 GB USERDATA** → ❌ 几十秒后掉线、设备离总线
- **约 3 GB 是单次 dd 的安全上限**

而我们的目标**只是让原厂基带跑起来**，并不需要原厂那份 10 GB 的 userdata。

## 精简方案：只刷 BOOT + SYSTEM

| 分区 | 刷? | 理由 |
|---|---|---|
| **BOOT** | ✅ 刷原厂 | 26 MB，秒成。原厂内核是基带流程的一部分 |
| **SYSTEM** | ✅ 刷原厂 | 3 GB，已验证可行。含原厂 `mdm_helper`/`ks`/RIL 全套 |
| **USERDATA** | ❌ **不刷** | 10 GB，风险源。**让原厂首次开机时自动重建**（见下） |
| RECOVERY | ❌ 不动 | TWRP 留作退路（关键） |
| EFS / RADIO / m9kefs | ❌ 不动 | 现在是好的，刷了反而引入变量 |

### USERDATA 不刷会怎样
原厂 Android 首次开机若发现 /data 不可用，会**自动格式化并重建**。
所以**只要把现有 /data 清掉**（比刷 10 GB 快得多、也更安全）即可：

```
# 在 TWRP 里执行（几秒钟的事）
adb shell 'dd if=/dev/zero of=/dev/block/platform/15570000.ufs/by-name/USERDATA bs=1048576 count=64; sync'
# 只清头部 64 MB，足够让 ext4 头部失效 → 触发原厂重建
```
> 更干净的做法：TWRP 的 **Wipe → Format Data**（重建 ext4），但这会重建整个分区，
> 耗时较长。只清头部 64 MB 是最省事的等效手段。

## 执行顺序

```
1) 进 TWRP
2) bash scripts/flash-resilient.sh stock-extract/boot-stock.img BOOT
3) bash scripts/flash-resilient.sh stock-extract/system-raw.img SYSTEM
4) 清 USERDATA 头部（触发重建）
5) adb reboot  → 原厂 Android 7.0 首次开机（会自动格式化 /data）
6) 插 SIM 卡，确认双卡可用 → ★ 基准成立
7) 按 docs/备份-刷原厂-回滚-流程.md §2 抓基准数据
```

## 回滚（随时可用）

```
bash scripts/flash-resilient.sh backup-20261003-full/BOOT.img BOOT
bash scripts/flash-resilient.sh backup-20261003-full/SYSTEM.img SYSTEM
bash scripts/flash-resilient.sh backup-20261003-full/USERDATA.img USERDATA   # 10GB，需分块
```

## 为什么这个方案更好
1. **避开唯一会掉线的 10 GB 写入**（两次掉线都发生在这量级）
2. **不碰 EFS/RADIO/m9kefs** —— 保持基带状态干净，基准对照才有意义
3. **保留 TWRP** —— 随时能回滚
4. 达到目的所需的最小改动
