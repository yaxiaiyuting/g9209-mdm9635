## 二、★ modem 的 AMSS 形态：**8 接口复合设备**

原厂下 modem 是 `1-2`，8 个接口各绑不同驱动：

| 接口 | 驱动 | 用途 |
|---|---|---|
| `1-2:1.0` | `diag_bridge` | 诊断 |
| `1-2:1.1` | `diag_bridge` | 诊断 |
| `1-2:1.2` | `hsic_sysmon` | SFR 复位原因查询 |
| **`1-2:1.3`** | **`ks_bridge`** | **→ 创建 `/dev/efs_hsic_bridge`** |
| `1-2:1.4` | `mdm_bridge` | |
| `1-2:1.5` | `mdm_bridge` | |
| `1-2:1.6` | `qc_csvt` | |
| `1-2:1.7` | `ipc_bridge` | |

**对照 LOS 20**：modem 只有 `1-2:1.0` 一个接口，绑 `ks_bridge`（=PBL 的 `05c6:9008`），
**从未出现 8 接口形态**。

### ★ 由此推出 AMSS 模式的 PID
内核 `ks_bridge.c` 的 `ksb_usb_ids[]` 里，**绑到 interface 3** 的只有两条：
```c
{ USB_DEVICE_INTERFACE_NUMBER(0x5c6, 0x908E, 3), .driver_info = &ksb_efs_hsic_dev },
{ USB_DEVICE_INTERFACE_NUMBER(0x5c6, 0x909E, 3), .driver_info = &ksb_efs_hsic_dev },
```
→ **本机 AMSS 模式 PID 极可能是 `05c6:908E` 或 `05c6:909E`**（而不是之前猜的 9048/904C/9075）。
这也解释了为什么第 3 轮时子代理在固件里搜 `9048/904C/9075` **一个都搜不到**。

## 三、★★★ 关键认知修正：原厂 modem **不是**每次都由 AP 喂 12 镜像

原厂 logcat 里 kickstart 的**全部**事件都是 **memory dump / EFS 同步**，没有任何一次是"上传启动镜像"：

```
SAHARA_HELLO → HELLO_RESPONSE
SAHARA_MEMORY_DEBUG            ← ★ 是 MEMORY_DEBUG，不是 READ_DATA
SAHARA_MEMORY_READ  addr=0x6BA628 len=0x34   （读内存区表）
SAHARA_WAIT_MEMORY_TABLE
Base 0xE00000 Len 0x100000, 'm9kefs1'        （从 modem 读回 m9kefs1）
SAHARA_MEMORY_READ  addr=0xE00000 len=0x100000
Received: 1048576 bytes → 写出 /dev/block/modem/m9kefs1
SAHARA_RESET                    ← ★ 原厂**会**发 RESET
RECEIVED <-- SAHARA_RESET_RESP
!@ Sahara protocol completed
STATE <-- SAHARA_WAIT_HELLO     （下一轮，处理 m9kefs2…）
```

### 三条重要推论

1. **原厂下 modem 是"自己启动"的**（固件已持久化在某处 / 或 SBL1 从 AP 侧 EFS 直接读），
   AP 侧的 `ks` 只在需要 **EFS 同步**或**收集 dump** 时才介入。
   → 这与我们在 LOS 20 上"每次都要喂 12 个镜像"是**完全不同的启动模型**。
2. **原厂确实会发 `SAHARA_RESET`**（在 memory-dump 流程末尾），而且 modem 会回 `RESET_RESP`。
   我们之前基于"发 RESET 会让它重启"的结论只在**镜像传输流程**里成立，
   在 dump/EFS 流程里 RESET 是**正常且必需**的收尾。
3. **EFS 同步是"从 modem 读回"**（`m9kefs1` 从 modem 内存 0xE00000 读 1MB 写到
   `/dev/block/modem/m9kefs1`），方向是 **modem → AP**，不是 AP → modem。

## 四、原厂下确实在跑 EFS 同步

`dmesg` 里可见大量：
```
efs_hsic_bridge efs_hsic_bridge: ksb_fs_read, count:425984 space:409600 copied:16384
```
即 `ks` 正通过 `/dev/efs_hsic_bridge` 与 modem 做 EFS 数据交换 ——
**这条通路在 LOS 20 上从来没建立起来过**（桥不存在）。

## 五、与 LOS 20 失败现象的逐项对照

| 项 | 原厂 7.0（正常） | LOS 20（失败） |
|---|---|---|
| 内核 | **3.10.61** | **3.10.108** |
| modem 启动模型 | **自己启动**，AP 只做 EFS/dump | AP 每次喂 12 镜像 |
| USB 枚举 | **8 接口复合** | 仅 1 接口（PBL 9008） |
| `/dev/efs_hsic_bridge` | **存在** | **从未出现** |

| EFS 同步 | 持续在跑（`ksb_fs_read` 刷屏） | 无从进行 |
| `MDM2AP_STATUS` | 常驻高 | 约 11.2 s 后掉 |

## 六、下一步（据此修正方向）

1. **确认 AMSS PID**：需要 root 读 `/sys/bus/usb/devices/1-2/idProduct`（当前 shell 无权限）。
   → 让用户在开发者选项里开 **Root access = ADB only**，或刷一个 root。
2. **对照原厂内核源码**：`3.10.61` vs `3.10.108` 在
   `drivers/usb/misc/ks_bridge.c` / `drivers/esoc/` / `drivers/usb/host/ehci-s5p.c`
   的差异 —— **这是最可能藏着根因的地方**。
3. **验证"modem 自己启动"的机制**：原厂下 modem 固件存在哪？
   （RADIO 分区是 FAT，只有 EFS；那 SBL1/AMSS 从哪来？）
   → 需要 root 后读 `/proc/cmdline`、`/sys/module/*/parameters/*`、以及原厂 `init.baseband.rc`。
4. **一旦确认 PID**，在 LOS 20 上就能定向验证：
   modem 是否根本没切 PID，还是切了但内核没认（驱动表缺项）。
